## Гипотезы (проверить, не поверить)

- `4294974469` ↔ спека `building-bonus-absorption` (shipped `v0.51.665`, 10.09 — **в проде**).
  Совпадение темы ≠ совпадение дефекта: жалоба про **видимость в зависимостях постройки**, спека —
  про поглощение бонуса. Если это разные вещи, вердикт «устранено» ставить нельзя.
- `4294974508` и `4294974616` — вероятно один дефект «Навес». Разведи или объедини явно.
- `4294974283` — май, до ADR-150 и до `beacon-install-discoverability`; «центр телепортации» мог
  быть заблокирован условием, а не сломан (тогда вердикт — про lock-state, а не про «починили»).
- Мульти-база: `memory/map/bases.md` — налог per-base (ADR-122), дубли зданий разрешены намеренно,
  открытый хвост «штраф при сносе одной базы из нескольких». «Максимальный уровень, десятый» пахнет
  тем, что апгрейд читает не ту строку `character_buildings` (`first()` без `orderBy` врёт при
  множественности) — но это гипотеза, доказательство = SELECT по её персонажу + прогон.

## Non-goals

- Не чинить. Ни строки в `app/`, ни миграции, ни теста — даже если дефект очевиден и правка в две
  строки. Найденное уходит в поле «Чем доказано» и дальше в отчёт владельцу.
- **Не считать коммит в `develop` или ветку `vulyk/*` доказательством «устранено»** — для этого
  есть отдельный вердикт.
- Не заходить в MCP Chrome и Telegram Web: браузер и тест-чар держит story 07. Нужен тап или
  нечитаемое вложение — пиши пункт по C4.
- Не выносить вердикт по жалобам соседних доменов (склад, крафт, дроны), даже если они всплывут
  в том же наборе сообщений.
- Не полагаться на «Main уже ответил» — его статус в ветке это гипотеза (assumption 4 плана).
- Не писать в прод. На testbot мутации разрешены, но со снимком «до» и восстановлением.

## Findings

Мульти-база несёт два живых прод-бага одного класса «первая строка — не та строка», ни один не
покрыт правкой ни в `develop`, ни в `vulyk/*`:

- `TextMapService:127-130` — своя база на карте резолвится через `claimedCellModel->where('character_id', ...)->where('status', 'active')->first()` без `orderBy`; берётся только ПЕРВАЯ активная база персонажа. У Анжелы (`character_id=1107`) первая база — `map_cell_id=767753`, вторая — `39833`; вторая на карте не отмечена ни как «своя», ни как «чужая» — рисуется обычной неизвестной клеткой (`mid 4294974671`).
- `BuildingUpgradeValidator:83-85` — апгрейд ищет постройку персонажа по общему шаблону `building_id` (одинаковому для всех баз), тоже без фильтра по `map_cell_id` и без `orderBy`/`.first()`. Для того же character_id=1107 запрос `character_buildings WHERE character_id=1107 AND building_id=5` вернул Теплицу первой базы (`level=10`), хотя апгрейдить пытались L1-Теплицу второй базы (`map_cell_id=39833`) — бот отвечает «уже максимум (10)» (`mid 4294974674`).

Оба места читают «первую попавшуюся» строку персонажа вместо строки нужной базы — при
мульти-базе (ADR-122, дубли зданий разрешены намеренно) это системная дыра, а не два отдельных
бага: любой сервис, резолвящий состояние персонажа/базы через `first()`/`find()` без `map_cell_id`,
рискует тем же классом отказа. Оба подтверждены прямым прод-`SELECT` на данных живого игрока, без
гипотез.

Отдельно, вне scope этого набора жалоб: легаси-броня (`ArmorDrifterClothes2Action` и однотипные)
проверяет наличие «Верстак 1» через таблицу `buildings`, в которой строки `name_en='WorkbenchOne'`
нет вовсе — чек всегда молча пропускается (латентный баг, слишком мягкий гейт, не относится к
жалобе `4294974469`, но стоит на заметке для отдельной story).
