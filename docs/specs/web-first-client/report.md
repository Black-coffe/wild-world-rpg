# Report — web-first-client: сайт как клиент №1, Telegram — альтернатива

**Date:** 2026-09-23 · **Deliverable:** document (study) · **Brief:** [`brief.md`](./brief.md)
**Recon:** 2 разведчика (веб-поверхность; связность ядра с Telegram) + read-only SQL на проде + ADR-061.
Числа ниже — `git grep`/`git ls-files` по `develop@2681c8a7` и SELECT'ы на проде 2026-09-23.

## 0. Коротко

1. **Играть на сайте сегодня нельзя.** Ни один публичный маршрут не меняет состояние игры, персонажа
   можно создать только через `/start` в боте (`StartCommand.php:91`). Весь «веб-клиент» — это
   статический прототип `public/webgame-preview.html` (gitignored, 94 экрана, **100 % mock**, ноль
   `fetch`). Реально на сайте живут: карта `/map` (+ своя позиция), профиль, достижения (+ свой
   прогресс), бои, вики, калькулятор крафта.
2. **Вход на сайт сам зависит от Telegram.** Единственный вход игрока — Telegram Login Widget
   (ADR-061), который грузится с `telegram.org` и подтверждается в Telegram. При блокировке/замедлении
   Telegram он ломается первым — ровно в том сценарии, ради которого делается веб. Первое, что нужно, —
   **свой аккаунт, не зависящий от Telegram**.
3. **Ядро игры наполовину переносимо, презентация — нет.** ≈55–60 % игровой логики лежит в сервисах
   и вызывается без Telegram; ≈80 handler'ов мутируют БД сами; 1 160 вызовов `Request::` в 303
   файлах, 1 853 `callback_data`, Markdown/HTML вперемешку. Клиент-нейтрального слоя экранов нет.
4. **Рекомендация — «мост + удушение» (вариант A):** web-клиент на первом шаге гоняет **те же**
   ~326 маршрутов бота через перехват транспорта (`Request::setClient`) и рендерит перехваченные
   сообщения и кнопки в браузере → паритет со всей игрой за одну фазу, а не за 326 портов. Затем
   самые частые экраны (карта, персонаж, база, крафт, задачи) заменяются **нативными** веб-экранами,
   которые сильнее Telegram. Telegram остаётся вторым клиентом того же ядра.

## 3. Варианты архитектуры

### A. Мост + удушение (strangler) — **рекомендую**

**Шаг 1 — мост.** Web-клиент шлёт на `POST /play/act` намерение `{kind: callback|text|command, data}`.
Сервер собирает синтетический Telegram-`Update` для персонажа игрока, прогоняет его через **тот же**
диспетчер (`CallbackqueryCommand` / `GenericmessageCommand` / команды), а транспорт подменён через
`Request::setClient()` (есть в longman/telegram-bot 0.81.0 — `vendor/…/Request.php:387`; проект уже
использует его в `TelegramDeliveryProbe`) на перехватчик: `sendMessage` / `editMessageText` /
`sendPhoto` / `answerCallbackQuery` не уходят в Telegram, а складываются в ответ, который браузер
рисует как экран: текст (Markdown → HTML), фото, inline-кнопки → кнопки, reply-меню → нижний док,
force-reply → поле ввода.

- Даёт **паритет со всей игрой** сразу — все 326 маршрутов, все механики, те же правила, те же гейты
  баланса и `ConditionalWriteService`. Никакой второй реализации правил.
- Edit-in-place ложится на веб естественно: «редактировать сообщение» = заменить экран.
- Пуши TaskHandler'ов для web-игрока перехватываются тем же способом и пишутся во **входящие**
  (таблица-outbox), которые клиент читает polling'ом.

**Шаг 2 — нативные экраны.** Самые частые поверхности (по firehose: callback 82 %) переписываются в
нативный веб-UI поверх JSON-API — карта с живой позицией, персонаж/инвентарь drag-free, база, очередь
крафта с таймерами, задачи. Каждый такой экран вызывает **сервис**, а не handler — это заставляет
выносить логику из handler'ов в сервисы, чем выигрывает и Telegram. Мост остаётся фолбэком для
редких экранов.

*Почему он:* единственный вариант, где игрок получает полную игру в вебе за одну фазу, а качество
«лучше Telegram» наращивается итеративно, экран за экраном, без замораживания бота. Минус — на
шаге 1 веб выглядит «как Telegram в браузере»; это честная цена паритета.

### B. Сначала нейтральный слой экранов, потом клиенты

Ввести `Screen{text, actions[]}` DTO и intent-роутер, переписать ~296 handler'ов на него, затем
Telegram-адаптер и web-адаптер. Архитектурно чище всего, но это переписывание всей презентации до
первого играбельного результата; блокирует бот-разработку на месяцы. Отвергаю как **первый** шаг —
он становится естественным итогом варианта A (нативные экраны и есть Screen-слой, растущий снизу).

### C. Telegram Mini App (WebApp)

Не решает задачу: Mini App открывается внутри Telegram и требует его доступности. Отвергнут.

### D. Отдельный SPA / отдельный бэкенд

Второе ядро правил = дрейф баланса и двойная поддержка. Прецедент — `C:\Projects\wildworld`
(Django-переписывание 2025 г., заброшено). Отвергнут.

## 4. Образ целевого веб-клиента («лучше Telegram»)

Основа — навигация прототипа, она уже совпадает с ботом и проверена владельцем:

- **Мобильный первый.** Нижний док из 6 разделов (Мир · Я · Крафт · База · Дела · Ещё), шторки для
  подэкранов, большие тап-зоны, safe-area (`viewport-fit=cover` уже стоит). Десктоп: рейл + правая
  колонка «Что происходит сейчас».
- **Постоянный HUD.** HP/выносливость/золото/клетка/активная задача с живым таймером — видно всегда,
  без запроса «Я».
- **То, чего Telegram не умеет:** живая карта с кликом-по-клетке (путь, Поход прямо с карты),
  одновременно видимые очередь крафта и склад, фильтры/поиск по инвентарю и рецептам, таймеры
  обратного отсчёта, история событий, глубокие ссылки на любой экран.
- **Скорость.** Бюджет: первый экран < 1.5 с на 4G, действие → экран < 300 мс сервер; PWA с
  service worker (оболочка и шрифты офлайн), карта тайлами/WebP вместо 10.7 MB PNG.
- **Уведомления.** Входящие на сайте (колокольчик) + бейдж; Web Push — вторым шагом, после проверки
  его доступности у российских пользователей (не подтверждено, см. §7).
- **Информативность.** `/guide`, советы, вики — прямо в клиенте, контекстно к экрану.
- **Дизайн-система.** Только `wildworld-ui.css` (ADR-062): игровые компоненты сначала в `ui-kit.html`.

воронки: CTA сайта и анонсы ведут в веб-игру, бот — альтернатива.

## 6. Предметные ворота (для будущих спек)

- **Классификация:** Фаза 0 — 🟠 (новый attack surface, модель идентичности) → ADR «Web-first client
  и аккаунты». Фазы 1–3 — 🟡/🟢 в рамках этого ADR.
- **Баланс (ADR-024):** новых чисел нет — мост исполняет ту же логику. Тайминги polling/сессии — инфраструктура.
- **WipeManifest (ADR-087):** `accounts`, привязки личностей, outbox — классифицировать (accounts →
  IDENTITY_RESET/KEEP — решить в ADR).
- **Media-off (ADR-020):** мост рендерит `caption` как есть — ворота выполняются автоматически.
- **Discoverability/Onboarding/Guide/Tips:** вердикты — в спеках фаз; ориентир: совет «Играть можно на
  сайте» — **да** (категория навигации) после Фазы 1; раздел `/guide` «Веб-версия» — **да**.
- **PUBLIC-WEB FLAT (ADR-062):** игровые компоненты сначала в `ui-kit.html`; инлайн-радиусы `/map`
  (`map.php:47-48,71`) — уже нарушение, чинить в N2.

| R7 | Один персонаж, два клиента одновременно | правила уже атомарны (`ConditionalWriteService`); UX — «открыто в Telegram» |

**Вопросы владельцу:** (1) Web-only игроки — разрешаем регистрацию без Telegram вообще (рекомендую: да,
иначе цель не достигается)? (2) Нужна ли Фаза 1 «как Telegram в браузере» публично, или сразу
закрытая бета для текущих игроков (рекомендую: закрытая бета по коду из бота)?
