# `findAllActiveCells()` проверен на реальной таблице, а не подменён целиком

## Goal
Единственный новый метод модели этой спеки — `ClaimedCellModel::findAllActiveCells()` — перестаёт
быть непокрытым. Сейчас в `tests/unit/Services/World/TextMapMultiBaseTest.php` он подменён
анонимным подклассом целиком, то есть проверяется поведение теста, а не метода: ни фильтр
`status='active'`, ни `orderBy('id')` не исполняются ни разу. Убери фильтр статуса — карта начнёт
метить брошенные базы, а набор останется зелёным.

## Requirements
> На текстовой карте мира эмодзи 🏕 стоит на КАЖДОЙ активной базе персонажа, попавшей в окно карты, а не только на одной: у персонажа с двумя активными записями в `claimed_cells` обе клетки помечены 🏕.

## Что проверить
Новый тест на РЕАЛЬНОЙ таблице (не подменённая модель, не скан исходника):

- Персонаж с двумя активными базами получает обе строки.
- Строка со `status`, отличным от `active` (в частности `abandoned`), НЕ возвращается — даже
  когда она единственная и когда она идёт первой по `id`.
- Строки чужого персонажа не возвращаются.
- Порядок детерминирован и возрастает по `id` (посеять записи так, чтобы порядок вставки
  отличался от порядка `id`, иначе проверка ничего не доказывает).
- Персонаж без активных баз получает пустой массив, а не `null` и не исключение.

Проверка идёт через публичный метод модели на посеянных строках. Схему таблицы `claimed_cells`
брать из миграции `*CreateClaimedCellsTable*` (и её `Add*`-довесков), а не писать по памяти;
таблицу создавать под своим приватным префиксом, как это уже сделано в
`tests/unit/Player/BuildingUpgradeBaseScopeTest.php` (`bubs_*`), чтобы не драться за общие имена
с параллельными агентами.

`app/Models/ClaimedCellModel.php` в `## Files` — на случай, если тест вскроет расхождение
(например, отсутствующий фильтр или нестабильный порядок). Правка модели допустима ТОЛЬКО как
реакция на красный тест и должна быть названа в `## Implementation notes`; если модель ведёт
себя верно — файл остаётся нетронутым, и это нормальный исход истории.

## Implementation notes

Новый файл `tests/unit/Models/ClaimedCellFindAllActiveCellsTest.php` исполняет
`ClaimedCellModel::findAllActiveCells()` напрямую (анонимный подкласс подменяет только
`$table` на приватную таблицу `facc_claimed_cells` — сам метод не переопределён). Схема
таблицы — 1:1 с `2024-05-23-061031_CreateClaimedCellsTable.php`, без FK (тот же паттерн, что
`BuildingUpgradeBaseScopeTest`). `app/Models/ClaimedCellModel.php` не тронут — метод вёл себя
верно, правка не потребовалась.

Ручная проверка (сломать → прогнать → вернуть как было):

1. Убрал `->where('status', 'active')` из `findAllActiveCells()`, прогнал файл точечно →
   2 падения: `testAbandonedBaseIsExcludedEvenWhenAloneAndFirstById` (ожидался `[]`, реально
   вернулась заброшенная строка) и `testAbandonedBaseIsExcludedWhenMixedWithActiveOnes`
   (ожидался 1 элемент, реально 2). Вернул фильтр обратно, сверил `diff` с `git show HEAD:...`
   — идентично.
2. Убрал `->orderBy('id', 'ASC')` целиком (оставил только `where` + `findAll()`), прогнал файл
   точечно → **все 6 тестов остались зелёными**. Причина — InnoDB для этого запроса (равенство
   по `character_id`+`status`, без вторичного индекса, конфликтующего по ключу) физически
   сканирует кластерный индекс по PK и для 3 маленьких строк детерминированно возвращает
   восходящий порядок по `id` даже без `ORDER BY` — это наблюдаемое поведение движка для
   такого размера таблицы и такого запроса, а не гарантия контракта MySQL. Критерий «тест
   падает, если убрать orderBy» в буквальном смысле (удаление клаузы) на этом стенде не
   воспроизводится.
3. Вместо этого сломал `orderBy('id', 'ASC')` → `orderBy('id', 'DESC')` (реалистичная порча
   детерминизма — тот же класс бага, что «переставили сортировку») и прогнал точечно → 2
   падения: `testReturnsBothActiveBasesOfCharacter` (`[1,2]` vs `[2,1]`) и
   `testOrderIsAscendingById` (`[1,2,3]` vs `[3,2,1]`). Вернул `ASC` обратно, сверил `diff` с
   `git show HEAD:...` — идентично, метод не тронут.

Тест `testOrderIsAscendingById` сеет строки в порядке `map_cell_id` 30→20→10 (обратном
желаемому выводу), чтобы `id` совпадал с порядком вставки лишь случайно — сам факт совпадения
`id` с порядком вставки в InnoDB (см. п.2 выше) и есть причина, почему точное «удаление orderBy»
не годится как ломающая мутация на этом стенде; «разворот сортировки» — рабочая замена,
проверяющая тот же инвариант (ORDER BY по `id` обязателен и именно по возрастанию).

Полный набор (`vendor/bin/phpunit --no-coverage --no-progress`, без флагов) в моменте гонки с
параллельными агентами волны давал 139, затем 43 разных ошибки — все `Table 'characters' already
exists` / `Unknown column ... in 'character_buildings'` / гонки на общих таблицах, ни одна не
упоминает `ClaimedCell`/`findAllActiveCells` (проверено `grep -i` по выводу). Это контентишн общей
локальной тест-БД от параллельно работающих агентов волны (см. `feedback_never_run_full_suite_in_parallel`),
не регрессия от этой story. Точечный прогон нового файла вместе с
`TextMapMultiBaseTest.php` и `BuildingUpgradeBaseScopeTest.php` — зелёный (19 тестов, 45 assertions).
