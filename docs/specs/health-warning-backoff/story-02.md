# Предупреждение приходит реже, если на него не реагируют

## Goal
После этой истории персонаж со стабильно низким здоровьем перестаёт получать одно и то же
сообщение весь день: каждое проигнорированное предупреждение отодвигает следующее, реакция
игрока возвращает базовый интервал, а ухудшение здоровья пробивает затухание немедленно.

## Requirements
> этот спам просто напрягает конкретно

> если человек на одно, два, три сообщения не реагирует, то просто забить нужно, на это не напрягать спамом

## Files
- app/Services/Player/HealthWarningSchedule.php
- app/TaskHandlers/LowHealthWarningHandler.php
- tests/unit/Services/HealthWarningScheduleTest.php

## Как это должно работать

Вся логика решения — в НОВОМ чистом классе `App\Services\Player\HealthWarningSchedule`:
на входе состояние (здоровье, `low_health_notified_at`, `low_health_warn_streak`,
`low_health_last_band`, дневной счётчик, время последней активности игрока, признак активного
damage-события, «сейчас»), на выходе — решение «слать / не слать» и новое состояние.
`LowHealthWarningHandler` только собирает вход, зовёт класс и применяет результат. Так логику
можно проверить тестом без БД и без Telegram.

Правила (числа читаются из `GameSettings`, ключи — в `brief.md`; хардкод 33 и 5 из хендлера
переезжает туда же и в коде не остаётся):

1. **Затухание.** Интервал = базовый × множитель^streak, обрезанный потолком. streak — число
   подряд проигнорированных предупреждений.
2. **Реакция сбрасывает.** Игрок «отреагировал», если в `player_action_log` есть хоть одна его
   запись позже `low_health_notified_at`. Тогда streak → 0 и интервал снова базовый.
   Запрос делай ОДНИМ обращением на весь пакет персонажей (в хендлере их может быть много),
   а не по одному на каждого в цикле.
3. **Ухудшение пробивает затухание.** Границы полос 5 / 3 / 1 / 0.1. Если текущая полоса НИЖЕ
   той, что записана в `low_health_last_band`, — шлём немедленно и сбрасываем streak. Возврат
   в полосу ВЫШЕ поводом для сообщения не является.
4. **Активное damage-событие** — как сейчас, повод предупредить чаще (короткий интервал), и
   тоже пробивает затухание.
5. **Дневной потолок.** Не больше `daily_cap` предупреждений за сутки вне критической полосы.
   Счётчик и дата — в новых колонках; при смене даты счётчик обнуляется.
6. **Критическая полоса** (`health <= 0.10`) живёт по своим двум ключам: короткий базовый
   интервал и свой, тоже короткий, потолок затухания. Дневной потолок к ней не применяется.

Текст сообщения, картинку и кнопки НЕ трогай — меняется только то, когда оно уходит.

## Tests
`tests/unit/Services/HealthWarningScheduleTest.php` — поведением, без БД, на новом чистом классе:
1. первое предупреждение уходит (состояния нет);
2. без реакции второе НЕ уходит через базовый интервал, уходит через базовый × множитель;
3. реакция игрока после предупреждения → интервал снова базовый, streak сброшен;
4. падение в полосу ниже → шлём немедленно, даже если затухание не истекло;
5. возврат в полосу выше сам по себе сообщения не вызывает;
6. дневной потолок исчерпан → не шлём (вне критической полосы), а в критической — шлём;
7. смена суток обнуляет дневной счётчик.
Тест обязан быть зелёным на ПУСТОЙ БД — CI гоняет без миграций, см. `.claude/rules/tests-db.md`.
