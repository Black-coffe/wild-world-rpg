# План: белый список типов PvE-наград

## Проблема (по разведке, не по догадке)

`app/Services/PVE/RewardService.php:228-262` `getRandomCraftedItems(int $count, bool $expensive)`
выбирает предметы **только по цене**: `where('price >=', 5000)` для сильного NPC,
`where('price <', 5000)` для слабого, затем `findAll()` + `shuffle()` + `array_slice()`.
Фильтра по `crafted_items.type` нет ни одного. `5000` — голый литерал, дважды инлайном
(строки 233 и 236), с комментарием «Порог подбирайте сами».

Вызовы: `grantRewards()` строка 108 (сильный NPC → `mt_rand(1,5)` предметов, «дорогой» пул)
и строки 111-115 (слабый NPC → бросок 50% → 1 предмет, «дешёвый» пул).
Входящие: `Services/Player/PvEService.php:128` (ручной бой), `TaskHandlers/NPC/AutoPveHandler.php:56`
(фоновый авто-PvE — тот самый поток «стоя на месте»), `Services/NPC/NpcInteractionService.php:399`.

Запись в инвентарь — `CraftedItemsLogModel` с `task_id => 1` и `crafting_location => 'all'`:
ровно отпечаток, названный в брифе.

`crafted_items.type` — `VARCHAR(100) NULL`, свободная строка, **не enum и не FK**.
Канонический перечень значений живёт в `CraftInsuranceService::TYPE_LABELS` (18 значений:
`drug, weapon, tool, food, clothing, building, component, transport, utility, decorative,
magical item, military, accessory, teleport, workbench, robots, defense, drones`).

Тестов на `RewardService` не существует ни одного.

## Решение

Повторяем живой паттерн `craft_insurance.eligible_types` (ADR-172, вчерашний коммит `a383c39f`):
CSV-список в `GameSettings` + геттер-парсер в сервисе. Ничего не изобретаем.

### Контракт ключей (решено здесь, оба воркера обязаны совпасть буква в букву)

Категория для всех четырёх — `combat` (уже существует, заведена
`2026-06-04-240000_W17SeedPvpDuelGameSettings.php`; новую категорию не изобретаем).

| `setting_key` | `value_type` | default | смысл |
|---|---|---|---|
| `pve.reward.craft_types` | `string` | `drug,food,component,tool,weapon,clothing` | белый список `crafted_items.type`, попадающих в розыгрыш |
| `pve.reward.price_cap` | `int` | `10000` | потолок цены предмета в пуле; `0` = без потолка |
| `pve.reward.expensive_threshold` | `int` | `5000` | заменяет магический литерал 5000; поведение при default не меняется |
| `pve.reward.type_filter_enabled` | `bool` | `true` | килсвитч: `false` → фильтр по типу и потолок не применяются, поведение как до фикса |

`recommended_min/max` и `hard_min/max` для `string` и `bool` игнорируются
(`GameSettingsService::isWithinHardBounds()` возвращает `true` сразу) — ставим `null`,
это канон, а не недосмотр. Для двух `int`-ключей границы заполняем.

`value_string` — `VARCHAR(255)`; наш список короткий, но список типов длиннее 255 символов
обрежется молча — держать в уме при правке из админки.

### Почему потолок цены нужен рядом с белым списком

Белый список отсекает роботов/верстаки/базы по типу, потолок ловит второй класс промаха —
дорогую позицию внутри разрешённого типа (`weapon` — не гарантированно дешёвая категория).
Два независимых рубежа, каждый гасится отдельно.

## Известные ловушки для воркеров

- **CI4 builder state quirk:** текущий код делает `$query = $this->craftedItemModel;`
  и вешает `where()` на общий инстанс модели. Два вызова подряд в одном процессе
  (а `AutoPveHandler` крутится в кроне) накапливают условия. Брать свежий инстанс
  или `->builder()`, не наследовать баг.
- `findAll()` тянет весь отфильтрованный каталог в память и `shuffle()`-ит его в PHP.
  Это не предмет story `-02` — не оптимизировать заодно.
- Соседний код в том же цикле (`durability_count` → `CraftedItemsLogModel::baseCharges()`)
  имеет собственную историю фиксов от 2026-08-09. Не трогать.

## Plan deltas

Дополнения после одобрения плана — по итогам замера на живом каталоге и отчёта `lead-review`
(вердикт: не мерджить). Первоначальный план был неполон в двух местах.

**Дельта 1 (story `-04`).** Дефолт `expensive_threshold = 5000` был задан как «поведение
не меняется» и не сверен с каталогом. Максимальная цена среди разрешённых типов — 500,
поэтому `price >= 5000 AND type IN (белый список)` даёт ноль строк: ветка «сильный NPC»
становится мёртвой. Порог опускается до 100, потолок — до 1000.

**Дельта 2 (story `-04`, из ревью).** Килсвитч заявлен как откат к дофиксовому поведению.
После снижения порога выключенный килсвитч раздавал бы почти весь каталог, включая роботов
и верстаки, — то есть был бы хуже исходного бага. При выключенном фильтре деление на пулы
обязано использовать исторический порог 5000. Обещание в докблоке и в rationale правится
тем же изменением.

**Дельта 3 (story `-05`, из ревью).** Все пять тестов задают настройки явными моками, поэтому
набор остаётся зелёным при ЛЮБЫХ дефолтах, включая пустой пул. Нужен тест, который краснеет
при расхождении констант сервиса с сиданными значениями миграции, и тест, который краснеет,
если дефолтная конфигурация даёт пустой пул на любой из веток.

**Решение по находке ревью №4 (темп крана).** `mt_rand(1,5)` предметов × `mt_rand(1,5)` штук
и бросок 50% на слабой ветке остаются как есть, admin-tunable не выносятся в этой спеке.
Причина: заявка человека — курирование ПУЛА, а не темпа; после дельты 1 в пуле остаются
расходники и компоненты по 5–500 золота, и худший случай фоновой победы это порядка тысячи
золота, а не 80 000, как было с роботом. Темп — отдельная задача, если замер покажет, что
он значим. Фиксируется здесь явно, а не пропускается молча.

**Решение по находкам ревью №6 и №7 (долг, не блокер).** Чтение настроек в `RewardService`
дублирует `GameSettingsReaderTrait`, а тест занимает общее имя таблицы `crafted_items`
в тестовой базе, как и четыре соседних теста. Обе вещи признаны и оставлены: первая — чтобы
не вносить лишний риск в изменение, которое чинит аварийный рычаг; вторая — потому что
совпадает со сложившейся практикой всех DB-тестов проекта и опасна только при параллельном
прогоне, которого у нас нет. Обе — кандидаты в `/vulyk-evolve`.

**Долг документации (из ревью №5).** `ADR-173` цитируется в трёх файлах, но не существует;
нота `mmorpg-vault/tech-writing/services/RewardService.md` не описывает курирование пула.
Закрывается на этапе build кастами `lead-architect` и `drone-docs`, не отдельной story.
