# Тесты, которые краснеют на плохом дефолте

## Goal
Набор перестаёт быть зелёным при любой конфигурации по умолчанию: появляются два кейса,
которые падают, если константы сервиса разъедутся с сиданными значениями миграции и если
дефолтная конфигурация даёт пустой пул на любой из двух веток.

## Requirements
> Все пять тестов задают настройки явными моками, поэтому набор остаётся зелёным при ЛЮБЫХ дефолтах, включая пустой пул. Нужен тест, который краснеет при расхождении констант сервиса с сиданными значениями миграции, и тест, который краснеет, если дефолтная конфигурация даёт пустой пул на любой из веток.

## Почему это важнее, чем выглядит

Именно из-за этого дефекта критическая находка доехала до человека зелёной. Пять кейсов
story `-03` перекрывают все четыре ключа явными моками, поэтому пустой «дорогой» пул
(порог 5000 при максимальной цене разрешённого типа 500) не уронил ни один тест.
Тест, который нельзя провалить неверным дефолтом, о дефолтах ничего не утверждает.

## Что покрыть

1. **Дефолты сервиса == сиданные значения.** Кейс читает значения из seed-миграций
   (обе: `2026-08-19-210000_Adr173SeedPveRewardPoolGameSettings.php` и ретюн из story `-04`)
   либо из таблицы `game_settings`, и сверяет с приватными константами `RewardService`.
   Расхождение — красный. Это ровно тот класс бага, который ловится только так: два
   источника правды, живущие в разных файлах и правленные разными воркерами.

2. **Дефолтная конфигурация даёт непустой пул на ОБЕИХ ветках.** Кейс НЕ переопределяет
   настройки (или переопределяет их ровно сиданными значениями) и проверяет, что и
   «дорогая», и «дешёвая» ветка возвращают хотя бы одну строку. Каталог для этого кейса
   сей ценами, воспроизводящими реальный порядок величин живой базы, а не круглыми
   удобными числами: разрешённые типы стоят от 5 до 500 (`drug` 5–40, `food` 20–40,
   `weapon` 15–50, `clothing` 50–200, `component` 70–420, `tool` 25–500), запрещённые —
   десятки тысяч (`robots` 95 000, `workbench` 120 000, `transport` 120 600).
   При пороге 5000 такой кейс обязан краснеть — проверь это, временно подставив 5000,
   и верни как было.

3. **Килсвитч действительно откат.** С `type_filter_enabled = false` пул обязан совпадать
   с дофиксовым: деление по историческому порогу 5000, без фильтра по типу и без потолка.
   Кейс должен краснеть, если выключенный килсвитч начнёт использовать настраиваемый порог, —
   именно этот регресс `lead-review` назвал критическим.

## Implementation notes

- Три новых кейса добавлены в `tests/unit/Services/PVE/RewardServiceTest.php`, пять кейсов
  `story -03` не тронуты (только добавлены `use`-импорты и таблица `game_settings` в
  `setUp()`/`tearDown()`/`TABLES` — она не используется старыми пятью, они по-прежнему
  работают через анонимный стаб `GameSettingsModel`).
- `testServiceDefaultsMatchSeededMigrationValues`: гоняет ОБЕ реальные seed-миграции
  (`Adr173SeedPveRewardPoolGameSettings`, `Adr173RetunePveRewardThresholds`) через
  `require_once APPPATH . 'Database/Migrations/<файл с датой-префиксом>.php'` — их FQN не
  резолвится через обычный `use`, потому что имя файла (с датой) не совпадает с именем
  класса, и PSR-4 classmap их не видит; тот же путь, каким идёт `php spark migrate`.
  Мигрирует в ephemeral `game_settings` (схема — по образцу `CreateGameSettingsTable`,
  создаётся/дропается в `setUp`/`tearDown`), затем читает 4 ключа через настоящий
  `GameSettingsService(new GameSettingsModel())` и сверяет с приватными константами
  `RewardService` через `ReflectionClass::getConstant()`. Красный подтверждён: временно
  поменял `DEFAULT_EXPENSIVE_THRESHOLD` 100→999 в сервисе, прогнал, увидел `Failed asserting
  that 100 is identical to 999`, вернул обратно (`git diff` после отката — пусто).
- `testDefaultConfigurationYieldsNonEmptyPoolOnBothBranches`: `serviceWith([])` без единого
  override — читает собственные дефолты `RewardService` (уже сверенные с БД предыдущим
  кейсом). Каталог — цены из story `-04` (drug 5–40, food 20–40, weapon 15–50, clothing
  50–200, component 70–420, tool 25–500; запрещённые robots/workbench/transport — 95к–120.6к).
  Красный на пороге 5000 подтверждён: временно заменил `serviceWith([])` на
  `serviceWith(['expensive_threshold' => 5000])`, прогнал — упало на дорогой ветке ровно с
  ожидаемым сообщением («порог 5000 при максимуме каталога 500»), вернул обратно.
- `testKillswitchOffUsesLegacyThresholdNotConfiguredOne`: один предмет ценой 800 — дороже
  настраиваемого порога (тест override'ит `expensive_threshold=100`, специально ОТЛИЧНОЕ от
  `LEGACY_EXPENSIVE_THRESHOLD=5000` значение, чтобы не совпасть случайно), дешевле
  исторического 5000. Красный подтверждён: временно заменил в
  `getRandomCraftedItems()` строку `$threshold = $filterEnabled ? ... : self::LEGACY...` на
  `$threshold = $this->expensiveThreshold();`, прогнал — упало на первой assertion (предмет
  за 800 не попал в дешёвую ветку, т.к. 800 ≥ 100), вернул обратно (`git diff` — пусто).
- **Находка про `testKillswitchOffRestoresPreFixBehaviour` (существующий, story `-03`).**
  Он остаётся зелёным после `f044d75a`, но это ложное спокойствие: оба сеяных предмета
  (`shed` price=200, `pricey_sword` price=800) дешевле И настраиваемого override'а в тесте
  (`expensive_threshold=1000`), И исторического `LEGACY_EXPENSIVE_THRESHOLD=5000` — тест
  проверяет только ветку `expensive=false` и никогда не проверяет ветку `expensive=true`,
  поэтому он в принципе не может отличить «килсвитч использует LEGACY=5000» от «килсвитч
  по ошибке использует настраиваемый override=1000»: обе гипотезы дают тот же зелёный
  результат на этих числах. Он валиден как регресс-тест на «тип/потолок не применяются при
  выключенном фильтре» (это утверждают его же assert-сообщения), но НЕ является тестом
  порога killswitch'а, вопреки названию `RestoresPreFixBehaviour`. Не переписывал его —
  story `-05` запрещает трогать пять существующих кейсов; регрессию по самому порогу
  теперь ловит новый `testKillswitchOffUsesLegacyThresholdNotConfiguredOne`.
