# CommunityGuard: пять рубежей против выуживания читов

## Goal
Появляется детерминированный привратник, без чьего разрешения ни один текст не уходит
в чат. Это ядро всей защиты из заказа: «чтобы люди не использовали его для того, чтобы
узнать какие-то фишки, лайфхаки и читинг». Первая редакция плана имела три рубежа, и
панель показала, что все три обходятся — рубежей пять.

## Requirements
> чтобы люди не использовали его для того, чтобы узнать какие-то фишки, лайфхаки и читинг в игре, и потом это не применяли

## Files
- app/Services/Community/CommunityGuard.php
- app/Config/CommunityStopTopics.php
- tests/unit/Services/CommunityGuardTest.php

## Non-goals
- Не отправлять и не матчить — гвард только выносит вердикт.
- Не читать `GameBalance.php` и `game_settings` ради «проверки, не совпало ли число»:
  опасный корпус не должен быть в зависимостях этого класса вообще.
- Не строить семантический анализ и не звать ИИ: рубежи детерминированные, иначе их
  нельзя покрыть тестом.
- Не решать судьбу входящего сообщения (удалить / ответить) — только «можно ли это сказать».

## Map slice
Опасный корпус, который НЕ должен быть в зависимостях: `app/Config/GameBalance.php`
(396 строк), значения `game_settings`, 30 файлов с `rarity|chance|probability` в
`app/Services/**`. Живые килсвитчи для рубежа 5 — grep `->get('...enabled')` по `app/`.

## Contract (из plan.md §5)
`verdict(string $answerText, string $questionText, ?string $requiresSetting): Verdict`
— `allow` / `manual` (в очередь владельцу) / `deny`.

1. **Провенанс предложений — главный рубеж.** Каждое предложение ответа обязано отображаться
   в дословный фрагмент белого корпуса (`GuideCatalog` адресами, `game_tips`, `glossary`,
   разрешённые `site_posts`). Нет источника — не `allow`. Это ловит разом весь класс утечек
   без цифр: «упирается в потолок», «Лаборатория выгоднее Мастерской», «ниже такой разницы
   уровней не срабатывает».
2. **Гвард на входящем.** Вопрос содержит число, диапазон, «%», слова
   потолок/максимум/порог/кулдаун, либо форму проверки гипотезы («правда, что…», «…, да?»)
   → не `allow` независимо от текста ответа. На «уворот же упирается в 75, да?» любой ответ
   читается чатом как подтверждение или опровержение — бот работает оракулом с одним битом.
3. **Лексический стоп-лист на исходящем.** быстрее / выгоднее / оптимально / всегда /
   никогда / достаточно / упирается / потолок / порог / перестаёт / бесполезно / окупается
   + числительные словами («сорок процентов», «вдвое», «раз в сутки»). Плюс запрет
   односложных подтверждений («да», «нет», «верно», «почти») как класса ответа о механике.
4. **Стоп-темы** (`Config\CommunityStopTopics`, уточнённый список §5.4 плана). Важно, что
   именно сужено: «пороги смерти» целиком — вредный запрет, режем проценты, а не тему;
   «подозрение на баг» — **не молчать**, а квитировать и эскалировать, иначе умирает канал
   баг-репортов.
5. **Live vs dormant.** Ответ, упоминающий подсистему за килсвитчем, обязан нести
   `requires_setting`; перед `allow` читается `GameSettings` — выключено, значит `deny`.
   Ответ про такую подсистему без заполненного `requires_setting` не проходит вовсе.

Плюс: **отказ без маршрута — запрещённый класс**. Любой `deny`/`manual` возвращает
маршрут из `Config\CommunityVoice::REFUSAL_WITH_ROUTE`, а не голое «не скажу».

## Acceptance criteria
- [ ] Предложение, которого нет в белом корпусе, не даёт `allow` — даже безупречное по тону.
- [ ] «Лаборатория окупается быстрее Мастерской» → не `allow` (рубеж 3), при этом в тексте
      ни одной цифры.
- [ ] Вопрос «уворот упирается в 75, да?» → не `allow` при любом тексте ответа (рубеж 2).
- [ ] «Сорок процентов» и «вдвое» ловятся так же, как «40%» (числительные словами).
- [ ] Ответ «да» на вопрос о механике → не `allow`.
- [ ] Ответ про транспорт с `requires_setting='world.vehicle.enabled'` при выключенном
      ключе → `deny`; при включённом → доходит до прочих рубежей.
- [ ] Ответ, упоминающий Оракул, без `requires_setting` → `deny`.
- [ ] Качественный ответ про смерть («теряешь часть опыта и статов, вещи с базы безопаснее»)
      → `allow`: сужение стоп-темы работает, полезное не зарезано.
- [ ] Каждый `deny` несёт маршрут; тест падает на отказе без маршрута.
- [ ] `CommunityGuard` не имеет в зависимостях `Config\GameBalance` — проверяется сканом
      импортов, но ЭТО НЕ ЗАМЕНА поведенческим тестам выше.

## Implementation notes

- `Verdict` — value-object живёт в ОДНОМ файле с `CommunityGuard` (story не вправе
  заводить 4-й файл вне `## Files`). PHP не требует один класс на файл; так как
  `CommunityGuard.php` всегда подгружается автозагрузчиком раньше любого обращения
  к `Verdict`, порядок объявления классов в файле не важен. `deny()` структурно
  требует непустой `route: string` (не nullable) — «отказ без маршрута запрещён как
  класс» гарантирован типом, а не соглашением; `manual()` — `route` опционален.
- Провенанс (рубеж 1) — НЕ строгий дословный substring на уровне предложения (русский
  язык сильно склоняется: «вещи»/«вещей», «база»/«базы»), а грубый детерминированный
  стемминг 3-символьным префиксом + порог покрытия значимых слов (≥60%) в ОДНОМ
  фрагменте корпуса (не вперемешку по всем документам — иначе можно собрать
  предложение из слов разных тем). Без семантики/ИИ, полностью тестируемо.
  Acceptance-пример «теряешь часть опыта и статов, вещи с базы безопаснее» проходит
  этим порогом против фрагмента про смерть/страховку (6/7 значимых слов), при этом
  выдуманное предложение без реальной опоры в корпусе (0% пересечения) не проходит.
- Рубеж 5 (`requires_setting`) и «канон-словарь» дормант-подсистем — в
  `Config\CommunityStopTopics::DORMANT_SUBSYSTEM_MARKERS`. Список сверен grep'ом
  `->get('*.enabled')` по `app/Services|TaskHandlers|Controllers` (нашёл ~90 ключей),
  но НЕ покрывает все — только явно названные в плане (оракул/дуэли/транспорт) плюс
  несколько очевидных. Расширяется по мере story 08+ и по мере того, как подсистемы
  переходят live/dormant.
- Баг-репорт (§5.4 «не молчать») даёт `Verdict::manual`, а не `deny` — семантически
  «в очередь владельцу» отличается от «политика запрещает»; в story 09 сейчас оба
  ведут к одинаковому `escalated` (гвард не решает КОГДА отвечать), но различие
  видно в reason-коде и пригодится story 12 (admin-очередь).
- `CommunityGuard`'s собственный docblock упоминает `Config\GameBalance` текстом
  (объясняя инвариант) — тест сканирует код БЕЗ докблоков/комментариев
  (`token_get_all` + фильтр `T_COMMENT`/`T_DOC_COMMENT`), иначе наивный substring-скан
  ловил бы сам себя как нарушение.
- `FORBIDDEN_PATTERNS` (§6 плана, story 04) добавлен в рубеж 3 как решение вне
  буквального текста Contract'а (там только 5 рубежей): единственная точка перед
  отправкой ЛЮБОГО текста (auto-reply story 09 И admin-одобрение story 12) — если
  здесь не проверить «обещание студии», это нигде не проверится вообще. Дешёвое
  дополнение (уже готовый список констант из `CommunityVoice`, не новый файл).
- Killswitch читается через `GameSettingsService`, инжектируемый в конструктор —
  паттерн 1:1 с `CommunityIngestServiceTest` (двойник `GameSettingsModel`), реальная
  таблица `game_settings` тесту не нужна. Корпус (рубеж 1) тоже инжектируется —
  дефолт собирает живой `GuideCatalog::sections()` + `game_tips` + `site_posts`
  (`canon_reviewed=1` + `published`), но unit-тест подаёт свой контролируемый корпус,
  не завязываясь на реальный prod-контент (который может задрейфовать).

## Findings

- ⚠️ Известный пробел: `glossary/` из плана (§5.1, часть белого списка) НЕ включён в
  `defaultCorpus()` — это markdown-файлы в `mmorpg-vault/`, соседнем репозитории, не
  гарантированно доступном рантайму прод-сервера (в отличие от `GuideCatalog`/
  `game_tips`/`site_posts`, которые все в БД/коде самого приложения). Нужно либо
  зеркалировать нужные глоссарий-статьи в БД/код при их использовании как источника
  ответа, либо явно исключить глоссарий из практического белого списка — решение за
  владельцем/следующей story, не блокирует story 07 (acceptance criteria его не
  требуют явно).
- `site_posts` фильтруется только `canon_reviewed=1 AND status=published` — плана
  §5.1 нюанс («флаг не сбрасывается после ребаланса, нужен список слагов или
  ограничение по дате сверки») НЕ реализован: это отдельное решение о процессе
  ревью постов, не про алгоритм `CommunityGuard`. Отмечено, не блокирует.
- `DORMANT_SUBSYSTEM_MARKERS` не претендует на полноту (~12 записей из ~90 найденных
  `*.enabled` ключей) — сознательный выбор в пользу explicit-и-проверяемого списка
  вместо угадывания всех возможных формулировок; расширяется по находкам.

### Приёмка Queen — враждебная проба рубежа 1 (сверх набора тестов)

Опасение: стемминг с порогом 0.6 мягче дословного провенанса из контракта, и через него
может пройти сравнительное утверждение, обходящее лексический стоп-лист. Проверено прямым
прогоном гварда против фрагмента корпуса про дрона:

| Проба | Вердикт |
|---|---|
| Добросовестный пересказ фрагмента | `allow` |
| «Дрон работает **быстрее**, чем ты сам» | `deny` / `lexical_stoplist` |
| «Дрон приносит **больше** ресурсов, чем ты сам» (в обход стоп-листа) | `deny` / `no_provenance` |
| «Дрона бери **раньше всего остального**» (в обход стоп-листа) | `deny` / `no_provenance` |
| Чистая выдумка про грибы | `deny` / `no_provenance` |

Вывод: дыры нет. Добавленное к источнику утверждение приносит слова, которых в источнике
нет, и покрытие падает ниже порога — рубеж 1 ловит сравнительные утверждения даже когда
рубеж 3 их лексически не знает. Порог 0.6 принят.

**Долги, уходящие в ревью явно:**
- `DORMANT_SUBSYSTEM_MARKERS` покрывает ~12 подсистем из ~90 найденных ключей `*.enabled`.
  Рубеж 5 работает только по известным ему именам; список обязан расти вместе с игрой.
- `glossary/` соседнего vault'а в корпус не входит — из прод-рантайма PHP он нечитаем.
  Корпус от этого уже, то есть строже, а не мягче.
- `FORBIDDEN_PATTERNS` из story 04 подключён здесь сверх буквы контракта. Решение принято:
  гвард — единственная точка перед отправкой ЛЮБОГО текста, и без этого список остался бы
  мёртвым кодом (тот же класс, что дефект связки в story 16).
