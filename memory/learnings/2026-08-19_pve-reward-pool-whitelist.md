# Урок: белый список без сверки с распределением данных даёт пустое множество

## Что случилось
План задал `pve.reward.expensive_threshold = 5000` с формулировкой «поведение не меняется»
и одновременно ввёл белый список типов. По отдельности обе половины верны. Вместе —
`price >= 5000 AND type IN (белый список)` даёт ноль строк, потому что самый дорогой
предмет разрешённого типа в живом каталоге стоит 500. Ветка «победил сильного NPC»
молча умерла. Поймано на ревью, не на планировании.

**Как ловить:** вводя фильтр по множеству ЗНАЧЕНИЙ рядом с существующим фильтром по
ДИАПАЗОНУ, посчитай их пересечение на реальных данных до того, как назначишь дефолты.
Один `SELECT COUNT(*)` с обоими условиями. «Не меняет поведение» — утверждение о
пересечении, и его надо проверять, а не предполагать.

# Урок: килсвитч-откат обязан иметь ФИКСИРОВАННУЮ точку отсчёта

## Что случилось
Килсвитч `type_filter_enabled` был заявлен как откат к дофиксовому поведению, но при
выключении делил пул по НАСТРАИВАЕМОМУ порогу. Пока порог равнялся историческому 5000,
обещание было правдой. Как только его опустили до 100, выключение килсвитча стало
раздавать почти весь каталог — включая роботов по 95 000 и верстак за 120 000, то есть
аварийный рычаг оказался бы хуже той аварии, от которой спасает.

**Как ловить:** если рычаг обещает «вернуть как было», его точка отсчёта не может быть
величиной, которую кто-то волен подкрутить. Фиксированная константа с комментарием,
почему она НЕ в GameSettings. И проверять обещание надо не в момент написания, а в момент
изменения любого параметра, на который оно опирается.

# Урок: тест с явными моками всех настроек не покрывает дефолты

Пять кейсов задавали все четыре ключа явно и оставались зелёными при любых значениях по
умолчанию, включая пустой пул. Именно поэтому дефект доехал до ревью незамеченным.
Нужен отдельный кейс БЕЗ переопределений — и кейс, сверяющий константы кода с сиданными
значениями миграции, исполняя саму миграцию, чтобы числа жили в одном месте.
