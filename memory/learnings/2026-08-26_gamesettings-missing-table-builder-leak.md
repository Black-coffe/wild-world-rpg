# Отсутствующая таблица game_settings копит состояние builder'а и течёт памятью

date: 2026-08-26
spec: community-chat-bot (story 66, побочная находка)

## Факт

`GameSettingsService` переиспользует один инстанс `GameSettingsModel`. Если таблицы
`game_settings` нет, `findByKey()` бросает `DatabaseException` **изнутри** `Model::first()` —
до штатного сброса состояния builder'а. Следующий `where()` на том же инстансе кладёт условие
поверх непойманного предыдущего, и при многих вызовах подряд состояние растёт неограниченно.

Локализовано исполнением (story 66): фиксированный синтетический корпус память не растит вовсе,
рост появляется только с реальным корпусом, где на каждый фрагмент идёт чтение настроек.
Это тот же CI4-квирк, что записан в `feedback_ci4_model_builder_state_quirk`, но триггерится
не циклом по ключам, а повторными вызовами через сервис.

## Почему это не только про локальную машину

Сценарий с отсутствующей таблицей воспроизводим **на проде в окне деплоя**: GitHub Actions
раскатывает код rsync'ом, и только потом `deploy/post-deploy.sh` применяет миграции. Между
этими шагами живой код читает ключ настройки, которого ещё нет. Один-два раза это безобидно,
но код, читающий настройки в цикле, в этом окне будет течь.

## Что делать

- Сервису настроек нужен `try/finally` со сбросом состояния модели (или свежий инстанс на вызов)
  — деградация «настройки недоступны → дефолт» обязана быть чистой, а не оставлять мусор.
- Диагностика такого роста памяти начинается с вопроса «а все ли таблицы на месте», а не с
  профайлера: `php spark migrate:status` дешевле.
- Не называть причину по памяти: первая версия объяснения ссылалась на `BaseConnection::$saveQueries`,
  которого в нашей версии CI4 не существует вовсе. Проверять `grep`-ом, что названное существует.
